# 数据库规范

## 基础约定

- 使用 MySQL 8.x 和 InnoDB。
- 使用 `utf8mb4`。
- 金额统一使用整数分，禁止浮点数。
- 时间统一使用 UTC 存储。
- 数据库结构变更统一通过 Alembic 迁移。
- 不修改已经应用的历史迁移。
- 不在应用启动时自动执行结构变更。
- 当前 MVP 使用单数据库，暂不拆库或读写分离。

数据库访问与事务边界的分层职责见 [系统架构](../architecture/overview.md#后端分层)。

异常回滚、并发冲突及提交结果不确定时的处理见 [错误与异常规范](../api/errors.md#事务与并发)。

## 主键设计

1. 所有实体表必须定义主键，优先使用单列代理主键，统一命名为 `id`。
2. **默认采用 UUIDv7**，MySQL 使用 `BINARY(16)` 存储，由应用层统一生成。
3. 纯内部、高写入量的表可采用 `BIGINT UNSIGNED AUTO_INCREMENT`；小型字典表可采用 `INT`。
4. 纯关联表可采用复合主键，是否使用代理主键根据实际需求决定。
5. 外键类型必须与被引用主键保持一致。
6. API 对外统一使用标准 UUID 字符串格式。
7. 禁止使用 UUIDv4 作为新建实体的默认主键，禁止使用 `CHAR(36)`、`VARCHAR(36)` 存储 UUID 主键。
8. 主键必须唯一、非空、不可变，不承载业务含义；业务唯一性通过 `UNIQUE` 约束保证。
9. 保留独立的 `created_at` 字段，不依赖 UUIDv7 判断精确创建顺序。

## UUID 编码与存量迁移

- UUID 按 RFC 9562 的原始字节顺序存储；Python 使用 `UUID.bytes`，MySQL 使用不启用字节交换的 `UUID_TO_BIN` / `BIN_TO_UUID`。
- ORM 统一转换 UUID 字符串与 16 字节存储值；业务层、会话与 API 使用标准 UUID 字符串。输入校验接受存量 UUIDv4 与新增 UUIDv7，不接受无连字符或带大括号的形式。
- 存量 UUID 保留原值，只转换存储格式；主键、外键以及审计中的 UUID 引用同步转换。
- 角色和关联表保留非空的 `created_at`，新增记录由应用生成 UTC 时间。缺少历史创建时间的存量记录以迁移时的 UTC 时间补齐，该值只表示回填时间。
- UUID 存储迁移在暂停应用写入并备份后执行；转换前校验全部非空 UUID，转换后核对记录、标识及关联关系，使用新增 Alembic 迁移保留历史迁移。
