# 文档治理规范

## 分类与权威范围

| 类别       | 位置             | 回答的问题                         | 维护方式                   |
| ---------- | ---------------- | ---------------------------------- | -------------------------- |
| 开发者手册 | `docs/handbook/` | 当前系统怎样，开发与运行应遵循什么 | 随实际交付持续维护         |
| 设计方案   | `docs/design/`   | 本次变更的目标、规则、取舍与影响   | 开发前确认，功能完成后冻结 |
| 实施计划   | `docs/plans/`    | 任务顺序、依赖、完成情况与验收     | 执行中更新，验收结束后结案 |

- 日常阅读从[手册入口](../README.md)进入，不通过多份历史方案拼出现状。
- 通用规范规定开发要求，模块手册描述已核实的当前行为；未实现的目标只进入已确认方案。
- 本次任务按现行手册和已确认方案实施；方案只在确认范围内改变目标，不自行扩大授权或覆盖其他规则。
- API 精确契约以 [OpenAPI](../../../openapi/openapi.yaml) 为准；手册解释业务语义，不重抄完整请求与响应。
- 文档与实现不一致时，先核实并明确差异；不能擅自修改业务规则或把实现缺陷改写为规范。

## 目录与命名

| 位置                     | 职责                                               |
| ------------------------ | -------------------------------------------------- |
| 项目 `README.md`         | 项目介绍与文档入口                                 |
| 项目 `AGENTS.md`         | AI 执行要求与权威入口                              |
| `handbook/standards/`    | 文档、开发、前端、测试、API、数据库等通用规范      |
| `handbook/architecture/` | 组件职责、进程边界、技术分层与依赖                 |
| `handbook/development/`  | 环境、配置、本地运行、数据准备与质量检查           |
| `handbook/modules/`      | 业务主题的现行规则、状态、权限与数据关系           |
| `handbook/operations/`   | 部署要求、备份及运行检查；业务恢复规则仍归所属模块 |

- `design`、`plans` **不设模块目录**，直接放日期前缀文件或专题目录。
- 单文件使用 `YYYYMMDD-topic.md`；大专题使用 `YYYYMMDD-topic/`，内部按实际主题拆分并提供 `README.md`。
- 日期取首次正式确认日期，计划沿用对应方案的日期和主题；不随日常修改改名。
- 后续迭代新增批次，同日用明确的不同主题区分；不得继续向已冻结方案或已结案计划追加功能。
- 文件使用稳定的英文 `kebab-case`；手册不加日期前缀。
- 一篇只负责一个明确主题。仅在职责混杂或阅读负担明显增加时拆分，不预建空目录、占位或固定套数的文档。
- 常规文档放入上述分类；不在 `docs/` 根目录新增正文，不另建日常日志或历史副本体系。

## 设计工作流

```mermaid
flowchart LR
    A[现行手册] --> B[提出设计]
    B --> C[人工评审与明确确认]
    C --> D[方案落盘]
    D --> E[取得实施授权并制定计划]
    E --> F[实施与验证]
    F --> G[同步现行手册]
    G --> H[冻结方案与结案计划]
    H -->|后续迭代| B
```

| 环节 | 要求                                                                             |
| ---- | -------------------------------------------------------------------------------- |
| 设计 | 写明问题、目标、范围、规则变化、关键取舍、影响与迁移，以及可验证的结果           |
| 确认 | 必须获得用户对当前方案的明确确认；评审结束或未提出异议不等于确认                 |
| 落盘 | 确认后、实施前保存正式方案，报告文件位置；未确认方案不得写为正式设计             |
| 实施 | 设计确认不等于授权修改代码，按用户针对实施的指令执行                             |
| 交付 | 核实实际交付范围，更新相关手册与契约；功能完成后方案冻结，全部验收完成后计划结案 |

- 方案以本次变化为主，通用约束引用手册；复杂主题按业务规则、数据、交互等需要拆分。
- 不遗漏当前任务所需的权限、并发、幂等、一致性、重复扣款防护、未知结果与异常恢复边界。
- 已授权范围内的常规工程保障按[开发规范](development.md#工程保障)自主补齐；业务规则、架构和授权边界变化仍需明确确认。
- 冻结方案只保留当时目标和决策依据，后续变化新增方案，不再同步为最新现状。

## 实施计划

- 工作量较大的任务在实施前落盘可勾选计划，写明范围、任务拆分、依赖顺序和验收条件。
- 执行中及时更新，只在完成并验证后勾选；代码完成、验收通过、已经部署分别判断。
- “同步相关手册与契约”必须列为交付验收项；未通过或未执行的条件继续保留。
- 业务规则引用手册或本次方案，不在计划中重新定义；结案只保留最终结果、验证范围和未完成条件。

## 表达与引用

| 内容                       | 优先表达                 |
| -------------------------- | ------------------------ |
| 组件、职责、依赖           | 架构图与职责表           |
| 实体、关联、关键字段       | 领域模型或 ER 图与字段表 |
| 状态、操作、前置条件       | 状态机图与条件表         |
| 多端协作、回调、异步处理   | 时序图                   |
| 数据产生、传递、保存与清理 | 数据流图                 |
| 权限、范围、例外           | 矩阵表或判断表           |
| 简单规则、操作步骤         | 短列表                   |

- 不写大段连续叙述；短段只解释必要背景，复杂条件改用图表。
- 图示按实际需要使用 Mermaid，不强制每篇画图；图、表和正文各有作用，不反复复述。
- 文档不得引用源码文件、路径、行号、类或函数，不嵌入实现代码、SQL、伪代码或源码目录树。
- 可以使用业务字段、状态、接口路径、配置项、文档目录和 Mermaid；操作指南仅列稳定使用入口，不抄写脚本实现。
- 仅引用文档与契约，使用相对 Markdown 链接，可指向章节；不能用“见代码”代替规则说明。

## 去重与内容边界

- 同一现行规则只在一个职责对应位置完整定义，其他文档引用，不通过不断追加“覆盖旧约定”维护现状。
- 手册不记录讨论过程、开发进度、逐次检查、排错重跑、临时机器信息、会话总结或变更日志。
- 变更过程放提交、PR 或交付讨论；原始日志、报告和截图放构建或交付附件，不建立第四类日常文档。
- 合并或精简必须保留适用范围、权限、关键条件、约束、风险和例外；不能靠删掉边界缩短篇幅。
- 术语统一：规范与约定说明共同要求，规格精确描述结构和行为，契约表达参与方可依赖的保证，协议定义通信规则。

## 维护与检查

1. 修改前检查现行权威位置与相关引用；手册原位维护，冻结方案新增批次。
2. 新能力按实际交付更新手册，不把计划、测试替身或未实现入口写成现有能力。
3. 文档治理任务检查全部文档；其他任务检查相关文档、调用关系与引用。
4. 完成后核对事实、职责、重复、源码引用、日期命名、链接与章节、Mermaid 和修改范围。
