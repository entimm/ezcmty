# 开发规范

本规范维护工程、安全、质量检查与 Git 要求。文档维护遵循[文档治理](documentation.md)，技术边界见[后端](../architecture/backend.md)、[后台](../architecture/admin-web.md)和[小程序](../architecture/miniapp.md)。

## 工程原则

- 遵循 KISS、YAGNI、DRY，优先简单实现，不为假设需求预建能力。
- 通用技术能力优先复用标准库、现有依赖及成熟方案，结合契约、安全性、维护状态和引入成本选择。
- 已有方案满足约束时直接复用；局部实现不能削弱业务规则与工程保障。
- 只修改当前任务直接涉及内容，不顺带重构；发现范围外问题记录建议。

## 组织与职责

| 对象       | 要求                                                                     |
| ---------- | ------------------------------------------------------------------------ |
| 模块和文件 | 围绕业务职责、依赖和变化原因组织，不以行数或“一类一文件”机械拆分         |
| 函数       | 表达明确操作，输入、输出和副作用可辨；编排与计算、访问、协议转换职责分明 |
| 类         | 管理相关状态、依赖或业务不变量；简单无状态计算不强制建立类或接口         |
| 命名       | 使用业务含义和具体职责，公共导出精简，避免万能公共模块或服务             |
| 依赖       | 显式传入必要协作对象，遵循所属层与业务端边界；循环依赖通过调整职责解决   |
| 副作用     | 事务提交、网络、任务和外部写入有明确归属，不藏在计算、格式化或读取中     |
| 复用       | 规则、权限边界和变化原因一致时才合并；有实际替换需求后再提取窄接口       |
| 修改       | 沿用合理相邻结构；共享能力变化检查全部受影响调用方及测试                 |

## 工程保障

- 在已授权范围内，主动补齐任务所需的并发控制、幂等、权限、数据一致性、重复扣款防护及异常恢复。
- 常规工程保障无需逐项确认，但不能借此改变业务规则、进程边界或扩大授权。
- 关键决策无法从需求确定时，按[自主决策与授权](../../../AGENTS.md#自主决策与授权)澄清，再推进依赖工作。
- 机制、限制与恢复条件写入对应方案或手册；交付报告实际验证结果、未完成项及遗留风险。

| 专题                 | 依据                                                               |

| 后台组件、视觉与交付 | [前端规范](admin-frontend.md)                                      |

- 密钥、密码、令牌不得硬编码、提交或写入日志；外部输入必须校验。
- 权限与数据范围由服务端执行，前端隐藏操作不能代替授权。

## 质量检查

| 范围       | 工具                                   |
| ---------- | -------------------------------------- |
| Python     | Ruff、mypy、pytest                     |
| TypeScript | ESLint、Prettier、TypeScript、Vitest   |
| 契约       | OpenAPI lint、构建与逐运行端一致性检查 |

- 修改后执行相关格式、Lint、类型、必要测试及构建，范围按风险确定。
- 未执行或未通过的检查不得声称通过；纯文档等低影响变更不机械新增业务测试。

## Git

- 提交信息采用 Conventional Commits，格式为 `type(scope): 中文描述`，简要概括本次变更，无需正文或逐项改动明细；必要技术术语保留原文。
- 大型功能模块实施前新建专用 worktree 和独立分支；同任务后续复用该 worktree。
- 其他非简单改动使用独立分支或 worktree，不为名称一致而重复创建已有任务工作区。
- 大型任务按业务独立性、多端协作、分阶段实施与验收综合判断，不单按文件数量判断。
- 当前任务完成后停止，不自行开始下一阶段。
