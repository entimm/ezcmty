# 开发规范

## 范围

本文件维护工程原则、安全、质量检查和 Git 约定。文档维护遵循 [长期文档治理规范](../standards/documentation.md)。

## 工程原则

遵循 KISS、YAGNI、DRY，优先选择简单实现。

## 代码组织与职责

本节规定通用编码要求。模块位置、分层依赖和调用边界遵循 [代码组织与账单支付接入](../architecture/code-organization.md)、[后端业务边界](../architecture/backend-services.md)、[管理后台前端设计](../architecture/admin-web.md) 和 [小程序架构](../architecture/miniapp.md)。

- **模块与文件**：围绕明确的业务职责组织，让一起变化的代码靠近，隔离因不同原因变化的代码。文件拆分依据职责、依赖及修改原因，不以行数或“一类、一表、一函数一个文件”作为机械规则。
- **函数**：表达一个明确操作，输入、输出和副作用可辨认。用例编排函数负责调用顺序，计算、校验、数据访问和协议转换放在所属能力中，避免混杂细节；不为了函数短小而拆出缺少独立含义的包装。
- **类**：用于管理相关状态、依赖或业务不变量。无状态的简单计算优先使用函数，不为命名或复用形式建立类、继承体系或接口。
- **命名**：使用业务含义和具体职责命名，保持同类能力一致。公共函数、类型和包导出保持精简；新增代码不随意归入宽泛的 `utils`、`common` 或万能 Service。
- **依赖**：显式传入必要协作对象，遵守所属层和业务端的依赖方向。发现循环依赖时调整职责归属或提取确有共用的能力，不通过隐藏导入或全局可变状态掩盖耦合。
- **副作用**：数据库提交、网络请求、任务安排及外部写入必须有明确归属，不能隐藏在计算、格式化、映射或属性读取中。事务边界沿用后端架构约定。
- **复用与抽象**：只有规则、权限边界和变化原因一致时才合并实现；相似代码不必强行共用。先使用具体实现，出现实际替换需求或稳定协作边界时再提取窄接口，不为假设中的未来功能预建框架或空目录。
- **修改与验证**：新增功能沿用相邻同类模块的合理结构，必要调整说明职责和依赖变化。拆分或提取公共能力时检查全部调用方及对应测试，不顺带重构无关模块；验证范围遵循 [测试规范](../conventions/testing.md)。

## 工程保障

- 代理应根据任务实际需要和风险，在已授权范围内主动设计、实现并验证并发控制、幂等性、权限校验、数据一致性、重复扣款防护、异常恢复等必要工程保障，无需用户提醒。
- 常规需求讨论无需逐项说明或单独确认上述保障。关键决策的澄清和授权要求遵循 [自主决策与授权](../../AGENTS.md#自主决策与授权)，不得以工程保障为由扩大任务或授权范围。
- 正式文档的记录要求遵循 [工程保障的文档要求](../standards/documentation.md#工程保障的文档要求)。
- 交付时简要说明关键保障措施、实际验证结果及遗留风险；未完成的验证和保障限制应明确说明。

## 安全

- 密钥、密码和令牌不得硬编码或提交。
- 敏感信息不得写入日志。
- 外部输入必须校验。
- 权限和数据范围必须由服务端执行。

## 质量检查

- Python 使用 Ruff、mypy 和 pytest。
- TypeScript 使用 ESLint、Prettier、TypeScript 和 Vitest。
- 修改完成后执行与改动相关的必要格式、Lint、类型检查和测试。
- 未执行或未通过的检查不得声称已通过。

## Git

提交信息使用 Conventional Commits：

```text
<type>(<scope>): <中文描述>
```

非简单改动使用独立分支或 worktree。任务范围控制遵循 [AGENTS.md](../../AGENTS.md#执行要求)。
