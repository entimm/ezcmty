# 后端业务边界与公共能力

## 分层与职责

各运行端显式组装自己的 API 和应用 Service。应用 Service 按后台及业务用例组织，负责操作权限、数据范围、状态流转、调用顺序和事务提交；同一资源在不同后台的业务流程分别维护。

公共业务规则按领域放入 `domain/`，当前管理员领域负责授权上下文、账号状态、会话版本、密码变更、RBAC 和审计归属规则。领域能力接收普通数据类型，通过 Repository 访问业务数据；不依赖 API Schema、应用 Service 或 Redis 会话存储，也不自行提交调用方的数据库事务。Repository、Model 和 Integration 按业务资源共用。

各端应用 Service 编排 Redis 会话读取、创建与续期，执行所属后台的公司校验、锁定顺序及事务提交。共用认证接口和携带会话数据的应用上下文放入 `services/contracts/`。`schemas/` 定义请求和响应模型，其 `mappers/` 接收已读取的记录、角色及权限，只做响应转换，不查询数据库或执行授权。配置、密码哈希、会话存储和运行就绪检查属于 `core/` 的技术机制。

各层职责和允许依赖如下，具体目录及支付接入见 [代码组织与账单支付接入](code-organization.md)。

| 层                    | 职责与依赖边界                                                                                                                                     |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| API                   | 处理 HTTP 参数、身份依赖、CSRF、状态和渠道 ACK，调用所属端应用 Service；不执行 SQL、提交事务或计算资金结果。                                       |
| 应用 Service          | 负责本端授权、范围、用例顺序、资源协调和事务；可调用 Domain、Repository、Integration 和纯 Mapper，不调用其他端应用 Service。                       |
| Domain                | 维护业务计算、事实核验、状态规则及共享账务变更；接收普通业务数据，可访问 Repository，不依赖 HTTP Schema、Service、会话存储或渠道网络，不提交事务。 |
| Repository            | 执行 SQL、范围过滤、行锁和持久化，依赖 Model；不决定用户授权、不调用渠道、不提交事务。                                                             |
| Model                 | 定义表映射、外键和约束，配合数据库保护；不承载用例、网络或后台调度。                                                                               |
| Schema / Mapper       | 表达公共契约及纯白名单转换；读取已加载的数据，不查询、授权或触发懒加载。                                                                           |
| Integration           | 封装外部协议、签名验签、解密、结构校验与普通事实转换；不决定入账、业务重试或资金状态。                                                             |
| 任务 Runner / Handler | Runner 负责领取、租约和生命周期；Handler 按任务类型及目标调用 Worker Service，不复制业务状态机。                                                   |

| ----------------------------- | ----------------------------------------------------------------------------------------------------- |

| `services/platform_admin/`    | 平台认证与本人操作、管理员与角色、物业接入、支付配置和授权范围内的资金管理。                          |
| `services/property_admin/`    | 物业认证与本人操作、本公司资料、房屋维护、账单线下操作及本公司支付资金只读。                          |

| `domain/admin/identity.py`    | 账号状态、会话版本、密码变更和 RBAC 规则。                                                            |
| `domain/admin/permissions.py` | 按后台定义的权限目录。                                                                                |
| `domain/admin/audit.py`       | 审计写入归属、读取权限与数据范围，返回业务记录。                                                      |
| `domain/housing.py`           | 空间父子类型、所属路径有效状态和业主手机号规范化规则。                                                |

各端路由工厂和应用 Service 固定所属后台，不接受切换后台或启用其他后台管理能力的开关。公共 HTTP 处理通过统一的认证与本人操作接口调用各端 Service；接口相同不表示业务编排相同。

## 身份、数据范围与事务

平台认证和应用 Service 只接受平台身份。物业认证从服务端账号解析公司，校验公司存在且启用；公司归属不来自客户端输入。物业应用 Service 只接受物业身份和明确的公司上下文。

读操作在各端 Service 校验后台、权限及数据范围后调用公共 Repository；公司过滤必须同时应用到记录、总数及分页。拥有相同权限码不能改变后台和公司边界。

物业登录、本人资料修改和改密由物业 Service 按公司、账号顺序锁定，并重新校验公司启停、账号状态和会话版本。平台接入管理继续按对应业务流程锁定公司及目标账号，遵循 [物业工作台设计](../design/property/workbench.md#登录密码与事务) 和 [物业接入设计](../design/property/onboarding.md)。公共身份能力处理密码、版本和审计记录，各端应用 Service 提交完整用例事务。

空间、房屋及业主维护沿用公司、账号锁定和身份复核，再按小区、空间祖先、房屋、业主的顺序协调资源；状态、范围和原子提交规则见 [房屋资料管理设计](../design/property/housing.md)。

计费依据、账单收款及纠错的事务和共享保护锁见 [账单设计](../design/property/billing.md#锁模式)，允许公司内独立账单并行写入。

公共审计和 Repository 使用明确的后台、公司归属；未知账号登录失败的归属及审计字段遵循 [管理后台基础框架设计](../design/admin/foundation.md#审计与代码组织)。Cookie、Redis 会话和权限目录按所属后台隔离。

各端 Service 通过公共领域能力协作，不调用其他应用 Service 的私有方法。跨端开通操作属于平台接入用例，保留平台操作者，显式解析目标公司和物业账号。

## 支付应用边界

支付规则与授权见 [居民账单支付与资金处理](../design/payment/bill-payments.md)，锁序与原子不变量见 [支付事务与并发](../design/payment/bill-payments-and-profit-sharing.md#事务与并发)。现有五个进程保持不变，Redis 不作为支付任务队列。

居民创建支付由居民 Service 校验当前身份和房屋授权，同事务提交订单、明细、占用及恢复任务。本人原订单读取和安全恢复与当前房屋授权分别判断；普通 GET 只读本地事实。调起参数由专门写操作签发，Service 可调用 Integration 本地签名，不重新下单。

平台 Service 负责商户与规则维护、并发配置令牌、恢复权限及审计。渠道能力核验在数据库事务外，提交前重新取得公司协调锁并验证配置条件。物业 Service 只读取本公司支付配置和资金结果，已有线下账单写入在账单锁内检查占用。

Webhook 读取原始字节，通过 Integration 验签、解密和结构校验，再由通知接收 Service 持久保存通知及任务后应答。不能重建 JSON 后验签，也不能在 ACK 前同步调用收款入账。非法通知和保存失败遵循渠道协议，不套内部 Problem Details；可信但无法关联或身份、金额不符的通知持久隔离。

`services/worker/payments/confirmation.py` 是唯一收款确认用例。通知处理和主动查询进入该用例，人工恢复及资金核对安排原业务任务。Service 协调支付 Domain 与 `domain/billing/posting.py`，原子提交支付成功、账务、应分与后续执行及任务、原占用释放；详情见 [支付确认与账单入账](../design/payment/bill-payments-and-profit-sharing.md#支付确认与账单入账)。账单 Domain 不反向依赖支付 Service。

分账和解冻由各自 Worker Service 编排，只在支付父记录上协调资金执行；不回头取得账单锁。核对 Service 组织文件获取、差异计算和证据保存，恢复仍进入原支付、分账或解冻任务，不直接把差异改为资金成功。

## 事务、渠道与任务

应用 Service 决定事务边界并提交或回滚，Domain 和 Repository 仅参与事务，可以 flush，不自行提交。HTTP 会话依赖负责异常清理及关闭，不自动提交；鉴权读取可能已经触发 SQLAlchemy 自动事务，不能机械嵌套事务。

应用 Service 决定用例所需锁及顺序，Repository 实现 SQL 锁。账单相关创建、入账和占用释放遵守支付数据设计的上级资源锁序；可以先读不可变关联确定锁对象，加锁后重新核验。真实收款确认仍取得必要保护锁，但不因当前解绑、启停或会话失效拒绝已经发生的收款。

| 操作               | 事务负责人                    | 提交边界                                   |
| ------------------ | ----------------------------- | ------------------------------------------ |
| 创建支付           | 居民 Payment Service          | 订单、明细、占用及恢复任务。               |
| 配置维护           | 平台配置 Service              | 配置、并发核验及管理员审计。               |
| 接收通知           | Webhook Service               | 去重后的通知与处理任务。                   |
| 确认收款           | Worker Confirmation Service   | 支付、全部账务、应分与后续任务、占用释放。 |
| 分账、解冻结果应用 | 对应 Worker Service           | 资金结果、后续任务和当前任务确认。         |
| 核对结果应用       | Worker Reconciliation Service | 汇总、差异、判定依据及恢复任务。           |
| 领取任务           | Task Runner                   | 仅领取、执行代次和租约，立即提交。         |

渠道操作采用四个阶段：保存 `started` 调用记录并提交，事务外请求渠道，保存可信响应证据并提交，在业务事务中核验和应用结果。入账失败不能丢失渠道成功证据；未知结果沿原业务单号和参数查询，不通过换单重试。

Worker 使用 Session 工厂，以独立短会话完成各阶段，不让 Session 或 ORM 对象跨越网络调用，也不在任务线程和续租线程间共享 Session。网络调用不得持有尚未结束的数据库事务或行锁。

Runner 按 [持久任务规则](../design/payment/bill-payments-and-profit-sharing.md#持久任务) 领取和续租；领取事务独立提交，不持任务锁等待业务锁。结果应用先取得业务锁，再校验任务 ID、执行代次及有效租约，业务结果与任务确认同事务提交。Handler 只适配任务目标，不决定资金重试或前置条件。

失去租约的旧执行者只能补存自己调用的迟到证据，不能覆盖接管后的任务或推进资金状态；当前执行者通过持久证据及原单查询恢复。任务重试间隔、暂停原因和资金恢复条件由支付用例决定，Runner 不内置支付状态规则。进程重启从持久任务恢复，不以重试次数耗尽作为放弃资金确认的依据。

## 接口与验证

外部路径、请求、响应、错误和运行进程归属继续以 [OpenAPI 契约](../api/openapi/openapi.yaml) 为准，内部代码组织不扩大各端已有接口集合。

验证覆盖各端路由集合、跨后台身份拒绝、公司查询隔离、受限会话、停用与会话撤销、密码变更与审计事务，以及真实 PostgreSQL/Redis 下的平台变更与物业操作并发。
