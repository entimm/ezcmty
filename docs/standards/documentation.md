# 长期文档治理规范

## 范围与术语

本文件统一定义项目长期文档的组织与维护要求。文档标题和正文按内容性质使用以下术语，避免混用。

| 术语                                 | 含义                                                                         |
| ------------------------------------ | ---------------------------------------------------------------------------- |
| 规范 / 约定（Standard / Convention） | 共同遵循的要求或做法；Standard 强调统一要求，Convention 强调一致的实践约定。 |
| 规则（Rule）                         | 单条明确、可执行的约束，可包含在规范、规格或契约中。                         |
| 规格（Specification）                | 对对象的结构、格式、行为和边界作精确描述，用于实现与验证。                   |
| 协议（Protocol）                     | 通信参与方遵循的消息格式、交互流程和语义，例如 HTTP。                        |
| 契约（Contract）                     | 接口参与方可依赖的输入、输出、错误、权限及行为保证等约定。                   |

OpenAPI Specification 规定 API 描述格式；项目 OpenAPI 文件表达 API 契约；HTTP 是通信协议。项目接口定义及其权威来源见 [API 规范](../api/conventions.md)。

## 设计工作流

新增或变更设计时，采用「方案设计 → 人工评审 → 明确确认 → 文档落盘 → 代码实施」的工作流：

1. **方案设计**：提交方案供评审，说明设计范围、规则、约束和关键决策依据。
2. **人工评审**：由用户审查方案，按评审意见调整尚未确认的内容。
3. **明确确认**：必须获得用户对当前方案的明确确认；完成评审或未提出异议不等于确认。未经确认的设计不得保存为正式设计文档，也不得直接实施。
4. **文档落盘**：经确认后创建或更新正式设计文档，仅记录确认范围内的内容；必须在对应功能实施前落盘，作为后续开发依据，并报告实际文件路径。
5. **代码实施**：设计确认不代表授权实施；正式设计文档落盘后，代码修改仍须遵循用户针对实施的具体指令及 [开发规范](../guidelines/development.md)。

## 组织与职责

- 根目录保留 `AGENTS.md`、`README.md` 等必要入口；常规文档放入 `docs/` 的主题子目录，禁止直接放在 `docs/` 根目录。
- `AGENTS.md` 维护项目级执行要求和权威文档入口，详细专题要求通过引用获取；`README.md` 提供项目介绍和使用入口。
- 按主题归属组织文档：`docs/architecture/` 存放系统级架构、部署及跨模块设计，`docs/design/<module>/` 存放业务模块详细设计，`docs/conventions/` 存放新增的通用开发规范与约定。
- 优先沿用现有合理结构：已有 `docs/standards/` 的跨主题规范、`docs/guidelines/` 的工程约定与指南，以及 `docs/api/`、`docs/database/` 的专题文档继续在原位置维护，不为统一目录名称进行不必要的迁移。
- 文件命名采用清晰、稳定的英文 `kebab-case`，名称应体现文档主题。
- 一篇文档负责一个明确主题，相关内容保持高内聚；仅在职责混杂或内容明显膨胀时拆分，避免过度拆分、集中或嵌套。
- 只在实际需要时创建目录和文档，不预建空目录、占位文件或重复文档。

## 单一权威来源

- 同一要求仅在一个位置定义，放入职责对应的文档；其他位置按需引用，保留必要背景，不复制维护同一约束。
- 引用使用相对 Markdown 链接，必要时指向具体章节；只将实际存在的文件或目录描述为已有内容。
- 合并或迁移要求时保留原有含义、适用范围和限定条件，并同步修正相关引用。
- 自动生成文档属于派生产物，不作为人工维护的另一份权威来源；OpenAPI 的具体组织和构建要求由 API 规范维护。

## 增量维护与检查

1. 新增或修改规范、设计前，先检查与现有架构、治理要求、相关规范和设计的一致性及相关引用，优先复用或合并已有内容；修改已有设计时优先更新原文档，不创建重复文档。
2. 按语义比较要求：已有的不重复添加，缺失的补充到权威位置，互补内容合并并消除冗余。
3. 对能明确判断的术语误用、重复定义、错误引用和组织问题直接修正。存在实质歧义或冲突时先说明并保留相关内容，不擅自改变已有约定、含义或选择一方。
4. 设计发生变更时，先按 [设计工作流](#设计工作流) 确认变更方案，再同步更新相关设计及其涉及的权威文档。
5. 修改范围遵循 [AGENTS.md](../../AGENTS.md#执行要求)。文档治理任务检查全部现有文档；其他任务检查相关文档和引用。
6. 完成后核对术语、职责、重复要求、引用有效性和改动范围，避免合并或删减导致必要约束丢失。

## 精简与稳定

- 文档和代码注释直接描述当前设计、行为与约束，保留理解和执行所需的细节，删除重复表述及无关内容。变更过程放在提交记录或 PR 描述中。
- 长期文档只记录稳定规范、规则、约束，以及已确认的设计与关键决策依据，不记录临时讨论、开发进度、任务状态、待办事项、执行记录、临时问题、会话总结或其他频繁变化的状态。
- 仅在稳定要求或架构约定实际变化时更新对应文档，不因普通任务完成而反复修改文档。
