# 测试规范

## 范围

本文件维护测试分类、组织、用例设计、依赖隔离、执行与维护要求，适用于后端、管理后台及其他运行组件。

测试工具和工程检查遵循 [开发规范](../guidelines/development.md#质量检查)，实际运行命令见 [本地开发指南](../guidelines/local-development.md#质量检查)。测试预期以业务设计、[API 规范及其权威契约](../api/conventions.md) 和 [数据库规范](../database/conventions.md) 为依据，本文件不重复定义业务规则。

## 分类与验证边界

| 分类     | 验证边界                                                           | 典型内容                                           |
| -------- | ------------------------------------------------------------------ | -------------------------------------------------- |
| 单元测试 | 单个组件的行为，协作依赖通过替身隔离，不启动真实外部服务或子进程。 | 业务规则、输入转换、响应映射、契约检查工具算法。   |
| 集成测试 | 多个组件的协作，或与数据库、Redis、进程等真实依赖的交互。          | API 与业务层联动、事务、迁移、并发、进程生命周期。 |
| 契约测试 | 权威 API 契约与各运行入口实现的一致性。                            | 接口集合、请求响应、错误、权限及进程归属的一致性。 |

- 分类由实际验证边界决定，执行速度作为独立属性；不能因为使用内存 Redis 替身或运行较快就将完整 API 回归归为单元测试。
- 契约检查工具自身的算法测试属于单元测试，使用项目权威契约验证运行入口属于契约测试。
- 数据库集成测试统一使用隔离 PostgreSQL，验证原生类型、行锁、并发冲突、迁移和真实约束。Redis 替身不能替代真实 Redis 协议与原子操作验证。

## 组织与命名

- 后端测试集中在 `services/backend/tests/`：单元测试归入 `unit/`，集成测试归入 `integration/`，实际契约一致性测试归入 `contract/`。只在存在相应测试时创建目录。
- 各分类内按业务模块或被测组件组织，再按登录、授权、审计、事务等稳定职责拆分文件；不按开发批次、修复日期或运行速度组织。
- 管理后台测试目录、模块组织和收集规则遵循 [管理后台前端设计](../architecture/admin-web.md#开发构建与检查)，在该组织内落实本规范。
- Python 测试文件使用 `test_*.py`，测试名称描述条件、行为或预期结果，使失败报告可以定位被验证的规则。
- 文件因职责混杂或内容膨胀而难以定位时拆分，不设机械的行数上限，不预建空目录或通用测试框架。

## 用例设计与覆盖

- 一个测试围绕一个业务结果，可以包含多个相关断言；独立的业务规则拆成独立测试，完整流程仅用于验证步骤之间的协作。
- 同一规则的多组输入优先参数化，各参数用例应可独立报告失败，并具有可识别的名称；避免在一个循环中验证多个独立场景。
- 优先断言返回结果、持久化状态、业务副作用和契约行为。仅在调用顺序或次数属于明确要求时断言内部交互，不机械复制实现逻辑。
- 根据改动风险选择必要验证层级；缺陷修复补充能够重现问题的回归测试，纯格式或文案调整不机械新增测试。
- 同一规则在多个层级验证时，各层应覆盖不同边界，例如计算规则与 API 联动；避免重复堆叠相同断言。
- 业务覆盖遵循相关设计的验证要求。修改共享能力时，执行覆盖受影响运行端的测试，不能仅验证一个调用端。

## Fixture 与资源隔离

- 测试文件不得导入其他测试文件中的 fixture、类型、常量或辅助函数。共享 fixture 放入最近的 `conftest.py`，共享替身、数据工厂和 Harness 放入职责明确的辅助模块。
- 根级 `conftest.py` 只维护全局环境、缓存清理等通用要求；集成测试共享数据库 fixture 放在 `integration/conftest.py`，业务初始化和专用依赖留在所属测试范围。
- 服务进程等高成本资源可按 session 复用；业务数据、Redis 键空间、客户端会话、环境变量、应用缓存及可变时钟必须按用例隔离。测试不依赖执行顺序，也不共享可变业务状态。
- 使用专用临时数据库、实例、目录和端口；资源必须属于当前测试，清理仅针对这些资源，不得连接既有开发或生产业务数据执行测试写入或清理。
- fixture 在失败时也必须释放连接、关闭进程并清理所属资源。验证提交、回滚或迁移的测试不得通过替身或 fixture 改写待验证的事务行为。
- 时间相关规则使用可控时钟；进程、异步和并发测试使用同步机制或有截止时间的条件等待，不依赖任意固定等待时间碰运气。

## 分级执行与结果判定

| 场景     | 必须执行的范围                                                 |
| -------- | -------------------------------------------------------------- |
| 开发过程 | 当前改动涉及的测试和相关回归；共享能力改动覆盖受影响的调用端。 |
| 每次 PR  | 全部单元测试、快速集成测试和契约校验。                         |
| 合并前   | 完整集成测试，包括真实 PostgreSQL/Redis 和进程生命周期验证。   |
| 发布前   | 完整回归及相关业务设计要求的关键流程验证。                     |

- 测试应支持按模块、文件和用例独立运行；慢速或依赖特定环境的测试通过明确的分类、配置或标记选择。pytest 标记必须在项目配置中登记，不能改变用例实际分类。
- 完整验证必须显式启用所需真实依赖测试。承担该范围的 CI 任务必须检查依赖可用性和测试结果；必需依赖缺失、目标测试未收集或整组跳过均应失败。
- 本地未选择运行的依赖测试可以跳过，但必须提供明确原因。结果报告需区分通过、失败、跳过和未执行，跳过或预期失败不计为通过。
- 测试操作说明和相关环境开关在本地开发指南集中维护；新增执行入口时同步更新指南，不将尚未实现的命令描述为可用入口。

## 持续维护与评审

- 关注测试耗时、跳过原因和偶发失败；CI 保留测试报告及定位失败所需的日志，按需要使用耗时统计定位瓶颈。
- 覆盖率作为发现遗漏的辅助指标，不代替关键规则、边界条件、事务和并发行为的验证。
- 偶发失败应修复资源隔离、同步或依赖问题，不用自动重跑掩盖。临时 `skip` 或 `xfail` 必须说明原因并关联问题跟踪，承担完整验证的范围仍按结果判定要求执行。
- 新增或修改测试时，评审应确认其分类、验证规则、依赖隔离和执行范围；测试整理应保留既有有效覆盖。改动范围与实施授权遵循 [项目执行要求](../../AGENTS.md#执行要求)。
